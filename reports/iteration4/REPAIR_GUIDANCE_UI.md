# 单元修复指导界面候选

候选 `app-repair-guidance.candidate.js` 从已通过红绿测试的回执刷新候选 `09357e…` 扩展，未覆盖原候选、生产源码或测试。精确文件哈希与部署入口见 `repair-guidance-ui-manifest.json`。

只对讲义工作流中 BLOCKED/FAILED 且后端提供有效 `repair_guidance_context` 的任务展示表单。用户必须选择实际单元，查看当前摘要并自行填写 20–20000 字指导；没有默认选中单元、现成证明或自动提交。说明明确限定一个单元，提交后继续原任务，仍须数学审阅、编译和交付检查，不代表教师批准。

草稿绑定任务、计划版本/哈希、章节及正文候选哈希。轮询、重渲染、HTTP 错误和网络错误均保留当前草稿；新候选不会自动继承旧正文的选中范围。相同提交内容失败后，用户手动再次提交复用 action_id；编辑正文或单元才生成新意图的 action_id。成功响应后清除对应草稿。没有自动重试。

POST 严格使用约定接口 `/api/runs/{id}/repair-guidance`，携带当前计划、候选正文、单个实际单元、指导文本与 `source: user`。页面不改写正文或数据库，不提交 `/reviews`。

本机实际 Edge 的九项合成 API/DOM 检查通过，证据 `repair-guidance-ui-validation/20260922-144924-4550b7/result.json`，含 trace、错误后保留草稿截图、四次合成 POST 的确切载荷及控制台记录。检查覆盖表单出现条件、空白初始值、正文摘要、实际定时器和强制重渲染、候选变更隔离、409/网络失败/503 草稿与幂等键、202 清除、FAILED 状态、非讲义工作流隐藏与无人审调用。源码及测试 SHA 未变。

该验证的接口全部由浏览器 mock；后端集成、真实模型、Windows 编译和教师审核均 NOT_RUN。需要在统一部署后执行正式 API 及完整 Edge 验收，不能把这九项界面检查记为真实工作流通过。原反馈刷新确定性红绿证据保持不变。
