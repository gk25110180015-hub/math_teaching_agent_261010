## 17 → 18 → 19 的纠错信息

已核对当前 `provider.py` 字节 SHA 与 retry2 执行前快照一致。事件保留错误与输入 hash，完整线缆请求体未归档，因此报告 JSON 中的纠错消息标为“由匹配的运行源码和已记录错误重建”，不冒称抓包证据。

- 请求 17 失败后，消息给出 `Invalid \\escape`、line 1、column 3612、offset 3611，要求检查所有 TeX 反斜杠并重新输出完整 JSON。它没有摘录 `\leq` 或另外两处 `\qquad`，也没有在纠错消息中给出完整合法 JSON 示例。
- 请求 18 失败后，给出 line 1、column 6354、offset 6353；仍只含标准解析器遇到的第一个错误，没有列第二处 offset 6419，也没有精确非法片段。请求 19 原样重复了请求 18 的错误正文。
- 初始 writer v2 提示本身已有合法 JSON/TeX 示例，并说明反斜杠须双写。现有纠错消息也明确要求不要只修第一处，因此不能归因于完全没有提示；更精确反馈属于可靠性改进。

原失败归档路径、每次 SHA、全部非法转义片段、请求与响应元数据、重建纠错消息及 checkpoint 清单见同名 JSON。实际 API 三次返回都有不同 response_id；未发现重试日志误计为同一次请求。第三次结束触发的是本次 schema 修复上限（初次 + 2 次修复），不是整任务 60 次预算耗尽。
